# Audio compatibility / 2026-10-01

## 報告と原因の仮説

追記：rc.4公開後、利用者から「iPhoneで音が出ました」と報告を受けました。基本の音声改善は利用者確認済みです。機種・OS・消音モードや復帰条件までは特定されていません。

利用者報告：公開候補rc.3でAndroidは音と手振りが動作し、iPhoneでは音が出なかった。機種・OS・ブラウザ・消音モード・出力先は未特定。原因が消音スイッチだけだったと確定した記録ではありません。

WebKitの[公式不具合記録237322](https://bugs.webkit.org/show_bug.cgi?id=237322)には、iOSの消音設定がWeb Audioに影響し、対応環境でAudio Sessionの`playback`指定を使えることが記載されています。[AudioSession.type](https://developer.mozilla.org/en-US/docs/Web/API/AudioSession/type)は対応が限られるため存在確認と例外処理を行います。[AudioContextの中断](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/state)も復帰時の確認対象です。これらは今回の症状に関する仮説の根拠です。

## rc.4の対応

- START／再開のクリック内で、非同期待機前にAudio Session設定、AudioContext.resume、確認音のsource.startを行う。
- 確認音は独自に合成。ミュートと音量設定を尊重する。録音素材・外部URL・マイクは追加しない。
- resumeのPromiseが解決しない場合も1.2秒の確認で準備を進め、画面に音声再有効化ボタンを残す。
- 音声時計の進行を確認する。`running`だけを根拠に準備完了としない。時計停止は診断と再有効化の表示へ反映する。
- 「音を試す」／「音を有効にする」のクリックで古いcontextを閉じ、新しいcontextと確認音を作る。ENERGY・時間を保持し、再生中の音楽を同期し直す。
- 明示的な音声復旧でミュートを解除する。音量0の場合は55へ戻し、スライダーと保存設定を一致させる。
- 音声中断による休憩からの再開ではcontextを新規作成する。タブ非表示・終了時には音源を停止する。

音声時計が進むことは、端末のスピーカーから聞こえたことの証明にはなりません。古いiOS等でAudio Sessionが使えない場合、端末の消音設定を解除する必要が残ることがあります。無音のメディアをバックグラウンドで常時再生する処理は追加していません。

## 実機の再確認

1. 全タブで運動を終える。更新案内が出た場合は更新し、URLを開き直す。
2. iPhoneの機種、iOS、ブラウザ、消音モード、端末音量、Bluetooth等の音声出力先を記録する。
3. 「カメラなしで試す」→確認音→手振り相当のドラッグ→HIT音・BGMを確認する。
4. START→カメラ許可→確認音／HIT／MOVEを確認する。音が出なければ音声ボタンをタップする。
5. 音量0、ミュート、スリープ、タブ復帰、一時停止／再開で復旧と成果保持を確認する。
6. `?debug=1`のaudioState／audioReady／audioTimeを端末内で確認する。診断を送信する機能はない。

デスクトップWebKitによる自動試験と、実機の消音・出力・復帰の試験を分けて記録します。
